# Skillar Mobile API Contract

**Status:** Target contract for implementation in `skiller-backend`  
**Consumer:** Skillar Mobile learner application  
**Base path:** `/api/v1`

This document defines the contract the mobile app will follow. It is not a list of currently deployed endpoints. The backend team should implement these routes and response shapes in `skiller-backend`. Do not make mobile screens depend on an endpoint until its contract and backend implementation are ready.

Administrative and organization-management APIs are not part of this mobile contract.

## 1. Global rules

### Base URL

The mobile client is configured with the backend origin, for example `https://[API_HOST]`. It appends `/api/v1` and the endpoint path.

Do not include `/api/v1` in `EXPO_PUBLIC_API_BASE_URL`.

### Headers

| Header | Requirement | Purpose |
|---|---|---|
| `Accept: application/json` | Every request | Response format |
| `Content-Type: application/json` | Requests with JSON bodies | Request format |
| `Authorization: Bearer <accessToken>` | Protected routes | Access authentication |
| `X-Request-Id` | Every request | Request tracing |
| `Idempotency-Key` | Supported create/submit operations | Safe retry of a mutation |

The backend must validate access tokens and enforce authorization. A mobile role or hidden screen is not an authorization boundary.

### Success response

Every response with a body uses this envelope:

```json
{
  "data": {
    "id": "resource-id"
  },
  "meta": {
    "requestId": "request-id"
  }
}
```

A successful response without a body uses HTTP `204 No Content`.

Paginated responses include pagination metadata:

```json
{
  "data": {
    "items": []
  },
  "meta": {
    "requestId": "request-id",
    "pagination": {
      "nextCursor": "opaque-cursor-or-null",
      "hasMore": false
    }
  }
}
```

### Error response

All non-2xx responses use the same shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid fields.",
    "details": [
      {
        "field": "email",
        "code": "INVALID_EMAIL",
        "message": "Enter a valid email address."
      }
    ]
  },
  "meta": {
    "requestId": "request-id"
  }
}
```

The backend must not return stack traces, SQL details, secrets or internal exception messages to the client.

### Conventions

- JSON field names use camelCase.
- IDs are opaque strings. The mobile app must not infer their format.
- Timestamps use ISO 8601 UTC strings.
- Date of birth uses `YYYY-MM-DD`.
- Optional values should be returned as `null` or omitted consistently. The chosen behavior must be defined per field.
- List endpoints use cursor pagination. Default page size is 20; maximum is [MAX_PAGE_SIZE].
- The backend owns validation, authorization and business rules.

## 2. Authentication

### Signup

`POST /auth/signup`

Request:

```json
{
  "name": "Learner Name",
  "email": "learner@example.com",
  "password": "[PASSWORD]",
  "dateOfBirth": "2000-01-31"
}
```

Response data:

```json
{
  "user": {
    "id": "user-id",
    "name": "Learner Name",
    "email": "learner@example.com"
  },
  "nextStep": "verify_email"
}
```

Allowed `nextStep` values: `verify_email`, `login`.

Signup does not issue an authenticated session unless the backend contract is deliberately revised. The mobile app follows the returned next step.

### Login

`POST /auth/login`

Request:

```json
{
  "email": "learner@example.com",
  "password": "[PASSWORD]"
}
```

Response data:

```json
{
  "user": {
    "id": "user-id",
    "name": "Learner Name",
    "email": "learner@example.com",
    "avatarUrl": null
  },
  "tokens": {
    "accessToken": "[ACCESS_TOKEN]",
    "refreshToken": "[REFRESH_TOKEN]",
    "accessTokenExpiresAt": "2026-11-16T15:00:00.000Z",
    "refreshTokenExpiresAt": "2026-11-23T15:00:00.000Z"
  }
}
```

Token expiry values are UTC timestamps generated by the backend. Actual token lifetimes are [ACCESS_TOKEN_TTL] and [REFRESH_TOKEN_TTL].

### Google sign-in

`POST /auth/google`

Request:

```json
{
  "idToken": "[GOOGLE_ID_TOKEN]"
}
```

The backend validates the Google ID token with the configured audience. The mobile app must never ship a Google client secret.

Response: same shape as login.

### Refresh

`POST /auth/refresh`

Request:

```json
{
  "refreshToken": "[REFRESH_TOKEN]"
}
```

Response: same shape as login, containing a newly rotated access and refresh token pair.

The backend must rotate refresh tokens and reject reuse of a token that has already been rotated. Mobile refresh requests are single-flight: simultaneous expired requests share one refresh operation.

### Logout

`POST /auth/logout`

Request:

```json
{
  "refreshToken": "[REFRESH_TOKEN]"
}
```

Response data:

```json
{
  "loggedOut": true
}
```

The backend must revoke the supplied refresh session. The mobile app clears its local tokens even if the network request fails.

### Email OTP

| Method | Route | Request body | Response data |
|---|---|---|---|
| POST | `/auth/otp/send` | `{ "email": "learner@example.com" }` | `{ "sent": true }` |
| POST | `/auth/otp/verify` | `{ "email": "learner@example.com", "otp": "[OTP]" }` | `{ "verified": true }` |

OTP expiry, retry limits and rate limits are enforced by the backend: [OTP_TTL], [OTP_RATE_LIMIT].

### Password reset

| Method | Route | Request body | Response data |
|---|---|---|---|
| POST | `/auth/password/forgot` | `{ "email": "learner@example.com" }` | `{ "accepted": true }` |
| POST | `/auth/password/reset` | `{ "token": "[RESET_TOKEN]", "newPassword": "[NEW_PASSWORD]" }` | `{ "reset": true }` |

The forgot-password response must not disclose whether an email address exists.

  "email": "learner@example.com",

## 4. Roadmaps

### Browse roadmaps

`GET /roadmaps?limit=20&cursor=[CURSOR]&q=[QUERY]&level=[LEVEL]&skillArea=[SKILL_AREA]`

All query filters are optional.

Response data:

```json
{
  "items": [
    {
      "id": "roadmap-id",
      "title": "Roadmap title",
      "description": "Short description",
      "level": "beginner",
      "totalHours": 24,
      "estimatedWeeks": 4,
      "language": "en",
      "skillAreas": ["Skill area"],
      "keywords": ["keyword"],
      "thumbnailUrl": null
    }
  ]
}
```

### Roadmap details

`GET /roadmaps/:roadmapId`

Response data contains:
- Roadmap metadata: `id`, `title`, `description`, `level`, `totalHours`, `estimatedWeeks`, `language`, `skillAreas`, `keywords`, `thumbnailUrl`
- Ordered milestones: `id`, `title`, `sequence`, `description`, `estimatedHours`
- Ordered steps in each milestone: `id`, `title`, `sequence`, `description`, `estimatedMinutes`, `contentStatus`

The API may return a lightweight list representation and a detailed representation. Mobile types must reflect that distinction.

### Enroll in a roadmap

`POST /roadmaps/:roadmapId/enrollments`

Request body: empty.

Header: `Idempotency-Key` required.

Response data:

```json
{
  "enrollmentId": "enrollment-id",
  "roadmapId": "roadmap-id",
  "status": "active",
  "enrolledAt": "2026-11-16T15:00:00.000Z"
}
```

A repeated request with the same idempotency key must not create duplicate enrollments.

## 5. Learning and progress

### List learner enrollments

`GET /me/enrollments?limit=20&cursor=[CURSOR]`

Response data contains `items` with `enrollmentId`, `roadmapId`, `title`, `status`, `progressPercent`, `startedAt`, and `lastActivityAt`.

### Get enrollment details and progress

`GET /enrollments/:enrollmentId`

Response data contains roadmap details relevant to the learner plus milestone/step progress.

### Get lesson content

`GET /steps/:stepId/content`

Response data:

```json
{
  "stepId": "step-id",
  "title": "Lesson title",
  "contentMarkdown": "# Lesson title",
  "video": {
    "provider": "youtube",
    "videoId": "video-id",
    "url": "https://www.youtube.com/watch?v=video-id"
  }
}
```

`video` may be `null`. Markdown is the primary content format.

### Update step progress

`PATCH /enrollments/:enrollmentId/steps/:stepId/progress`

Request body:

```json
{
  "status": "in_progress",
  "progressPercent": 50
}
```

Allowed status values: `not_started`, `in_progress`, `completed`.

Response data returns the persisted step status, percentage and `updatedAt`. The backend must validate that the step belongs to the enrollment and calculate aggregate progress.

### Assessment

| Method | Route | Purpose |
|---|---|---|
| GET | `/steps/:stepId/assessment` | Get assessment definition |
| POST | `/assessments/:assessmentId/attempts` | Create an attempt |
| POST | `/assessment-attempts/:attemptId/submit` | Submit answers |
| GET | `/assessment-attempts/:attemptId` | Get attempt/result |

Assessment submission request:

```json
{
  "answers": [
    {
      "questionId": "question-id",
      "selectedOptionIds": ["option-id"]
    }
  ]
}
```

Submission uses an `Idempotency-Key`. The backend owns scoring and must return the attempt result and feedback allowed for the learner.

## 6. Journeys

Journeys are learner assignments. The backend owns audience filtering, stage gating, completion rules and progress calculation. The mobile app must not infer access from hidden UI. Journey enrollment, stage, activity and assessment-attempt IDs are numeric database identifiers in this API; mobile types must keep them as numbers. Other API resources may continue to use opaque string IDs.

### List assigned journeys

`GET /me/journeys?limit=20&cursor=[CURSOR]`

Returns the authenticated learner's journey enrollments for the token's organization. Uses the standard cursor pagination envelope.

Each item contains:
- Enrollment: `enrollmentId`, `status`, `enrolledAt`, `dueAt`, `completedAt`, `currentStagePosition`
- Journey: `id`, `title`, `description`, `type`, `durationDays`
- Progress: `percent`, `totalStages`, `completedStages`, `totalActivities`, `completedActivities`
- `nextActivity`: the next activity in an unlocked stage, or `null`

### Journey enrollment details

`GET /journeys/enrollments/:enrollmentId`

Returns the learner's journey, ordered stages, ordered activities, stage progress, activity progress and assessment attempt summaries.

Activity metadata is filtered by the backend:
- `TASK`: task instructions and duration
- `VIDEO`: content URL and duration
- `DOCUMENT`: file display name and availability flag. Storage keys are never returned.
- `ROADMAP`: linked roadmap ID
- `ASSESSMENT`: question text and options only. Correct answers and scoring keys are never returned.
- `ACKNOWLEDGEMENT`: acknowledgement text

### Complete an activity

`POST /journeys/enrollments/:enrollmentId/activities/:activityId/complete`

No request body is required. The backend verifies enrollment ownership, organization scope, stage unlock state and activity type. It then persists completion and advances the stage or journey when the required activities are complete.

This endpoint does not complete `ASSESSMENT` or `ROADMAP` activities:
- Assessment activities remain read-only until a dedicated attempt/submission API is implemented.
- Roadmap activities are completed by completing the linked roadmap.

### Current mobile limitations

- Document activities do not yet have a signed-URL endpoint. The app must show an unsupported-content message and must not use an S3 key as a public URL.
- Assessment activities can be reviewed but cannot be submitted from mobile yet.
- SCORM is not supported in the mobile app.

## 7. Error codes

Initial standard codes:

| Code | Meaning |
|---|---|
| `VALIDATION_ERROR` | Request fields failed validation |
| `UNAUTHENTICATED` | Access token missing, invalid or expired |
| `SESSION_REVOKED` | Refresh session is no longer valid |
| `FORBIDDEN` | Authenticated learner cannot access this resource |
| `NOT_FOUND` | Resource does not exist or is not visible to the learner |
| `CONFLICT` | State conflict, such as duplicate or invalid enrollment |
| `RATE_LIMITED` | Rate limit reached |
| `INTERNAL_ERROR` | Unexpected backend error |

The backend should use standard HTTP status codes and stable error codes. Mobile behavior must use the code/status, not parse message text.

## 8. Security and operational requirements

- All production traffic uses HTTPS.
- Refresh tokens are revocable and rotated.
- Passwords and tokens must never appear in logs.
- Backend authorization is checked on every protected resource.
- Login, OTP, reset and assessment submission endpoints have rate limits.
- Request IDs are logged by the backend and returned in response metadata.
- Create/submit operations support idempotency where specified.
- Error details never include private learner data or server internals.

## 9. Contract governance

1. This document is the mobile/backend agreement until an OpenAPI specification is published.
2. The backend should publish an OpenAPI 3 specification from NestJS.
3. A breaking change requires a new API version or a coordinated migration.
4. Additive response fields are allowed. Removing or changing the meaning of a field is breaking.
5. Update this document and mobile runtime parsers in the same change as a contract change.
6. Do not create duplicate business logic in the mobile app. The backend remains authoritative.
